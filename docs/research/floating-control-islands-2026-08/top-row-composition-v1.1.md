# Floating Islands — навигация и контекст, v1.5

2026-09-05. Pattern `pattern.detached-chrome-control-islands`, существующий PR #47. Путь сохранён ради входящих ссылок. Core FI-01–20 и release bindings RB-01–03 продолжают действовать с адресными уточнениями ниже. Это документальное продуктовое решение и векторные схемы; новая runtime-версия или A=S=P PASS не заявлены.

## 1. Поправка владельца: desktop и mobile различаются по смыслу

В предыдущих растровых концептах была пропущена **desktop-навигация «Сегодня / Завтра / Выходные / …»**. Такие концепты не являются правильным baseline или источником состава интерфейса. Генерацию картинок для этой задачи прекращаем; обсуждаемые состояния оформляются в редактируемых SVG, без выдуманных фотографий, новых разделов сайта и подмены меню.

**Было → стало:** desktop-остров «Популярное + текущая полка», при этом меню потеряно → desktop-меню сохраняется, его активный пункт «Популярное» показывает текущую страницу, поэтому отдельный плавающий остров содержит **только текущую полку**, например «Набирают популярность».

**На mobile двойной остров сохраняется:** «Популярное» основным начертанием и название полки вторичным внутри одной поверхности. Дополнительную горизонтальную полосу разделов на mobile не добавляем. Второй смысловой уровень не означает обязательный второй отдельный остров или закреплённый этаж.

Ключевой инвариант: убрать дублирующую page identity можно только если другая **реально видимая и понятная** поверхность надёжно её сообщает. Само наличие где-то скрытого меню, viewport label `desktop` или ширина экрана этого не доказывают.

## 2. Что здесь называется меню

Это **навигация разделов с выделенным текущим пунктом**. Визуально она может выглядеть как сгруппированные сегменты, но это не toggle «вкл/выкл» и не обязательно ARIA tabs. Переходы между страницами остаются ссылками; текущая ссылка получает `aria-current="page"`. Раскрытия переполнения являются отдельными кнопками с понятными названиями и `aria-expanded`.

Не назначать всей обычной навигации сложные roles `menu/menubar/tablist` только из-за формы. Первичные основания: [W3C Disclosure Navigation](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/) и [Menu Structure](https://www.w3.org/WAI/tutorials/menus/structure/), прочитаны в этой итерации. Они не заменяют реальные keyboard/AT проверки проекта.

Desktop сохраняет свою установленную контекстную навигацию. Существующие нижние destinations остаются владельцами своих функций; новое верхнее меню другого состава не придумывается. На mobile вход в эти разделы остаётся через существующую брендовую бирку. Саму бирку не сжимаем и не переставляем.

## 3. Desktop: четыре понятных состояния

### До прокрутки

Неподвижная бирка и обычная навигация разделов, в которой «Популярное» уже выделено. В контенте остаётся настоящий H1 «Популярное». Он не считается лишним floating-дублем: это заголовок документа в начале чтения. Следом — реальная первая полка и карточки, видимые на первом экране.

Выбор городов начинается **развёрнутым рядом доступных вариантов**, а не одним закрытым «Все города ▾». Это не автоматически открытый popup и не огромное отдельное окно. Количество видимых вариантов определяется реальной выборкой и доступным местом; бесконечный список не обязан помещаться целиком.

### Переход к общей строке

H1 уходит с обычным контентом. **Он не создаёт ещё один плавающий «Популярное» рядом с уже выделенным пунктом меню.** Таким образом, прежнее требование плавного morph названия страницы теперь применяется к mobile/вариантам без видимой page identity, а не механически ко всем размерам.

На desktop компактным островом становится контекст полки; он и города входят в общую строку с навигацией. Преобразование начинается при фактическом движении, без внезапного клона после исчезновения оригинала; сохраняется непрерывная диагональная траектория, где она нужна, а не отдельный горизонтальный перегон. Все стадии должны обходить занятые биркой и меню области. Конкретная траектория вычисляется по реальной геометрии; диагональ не даёт разрешения провести текст сквозь меню.

### Закреплено

```text
[неизменная бирка] [Сегодня · Завтра · Выходные · … · ПОПУЛЯРНОЕ · …]
                  [Набирают популярность] [видимые варианты городов · Ещё города]
```

Перенос в текстовой схеме — только для чтения. **При достаточной ширине все эти блоки занимают одну горизонтальную строку.** У навигации, полки и городов отдельные поверхности и свободные промежутки, не сплошной новый header slab.

На широком desktop можно оставить все пункты навигации и несколько городов. На более узком сначала убирается лишняя декорация, затем используются понятные раскрытия для части городов и, при необходимости, части неактивных разделов. Полное скрытие городов не является условием pinning.

### Смена полки

Из собственного ограниченного слота вверх уходит название прежней полки; снизу приходит название следующей. Размер слота не заставляет меню и города ездить из-за разной длины заголовков. **«Популярное» в меню не меняется:** скроллинг к следующей полке не является переходом на другую страницу.

Текущий scope определяется boundaries реальных sections. После последнего section контекст не зависает над footer; при обратной прокрутке возвращается предыдущий. Подходящий H2 остаётся семантическим заголовком в документе, не вторым активным деревом управления.

## 4. Компактный desktop: активная страница не должна исчезнуть

Допустимо вынести часть неактивных ссылок в **«Ещё разделы»**, а часть городов — в **«Ещё города»**. Это два разных раскрытия с разным содержанием, не два одинаковых безымянных многоточия. Внутри сохраняются остальные разрешённые destinations и реальные параметры выбора.

Пункт текущей страницы **«Популярное» остаётся видимым снаружи** независимо от исходной позиции в длинном списке. Его нельзя скрыть за «Ещё разделы», продолжая считать имя страницы понятным по одной полке.

Для особо тесного desktop допустим компактный навигационный trigger **«Популярное ▾»**, открывающий полный набор разделов. В этом случае page identity всё ещё видна в самом trigger; дополнительный floating title не нужен. Такой вариант требует явного view contract и проверки, а не принудительного сжатия на всех desktop.

Если навигация совсем скрыта или превращена в безымянную кнопку, условие замещения не выполняется. До восстановления видимого выбранного названия используется combined page+section identity, как на mobile, либо читаемый flow. Увеличение текста и уменьшение окна не должны оставить человека только с «Набирают популярность» без понимания страницы.

Система не скрывает меню или города просто от большого scroll offset. Компактизация вызывается действительной геометрией общей строки и явной composition policy. Выбранные города, focus, открытое раскрытие и held target защищены от внезапного переноса; увеличение доступного пространства обратимо с hysteresis. Сохраняются min-target и readable text, не уменьшаются шрифты ради числа видимых элементов.

## 5. Mobile: один двойной контекст и отдельные города

```text
[неизменная бирка] [Популярное              ] [города / …]
                  [Набирают популярность   ]
```

Две надписи находятся **внутри одного острова**: название страницы заметнее, дочерний контекст спокойнее. Это не два независимых pinned ряда. Города остаются отдельным действием; при нехватке места их trigger можно сократить до «…» с полным доступным названием. Эти точки не открывают общее меню.

До прокрутки H1/H2 остаются обычными заголовками и первая карточка уже видна. С первых пикселей прокрутки page label начинает плавное сокращение и диагональное движение к своему слоту, с постепенным формированием поверхности. Бренд не участвует в transform. Нет двух одновременно читаемых копий «Популярное» или последовательности «сначала вбок, затем вверх».

Когда следующий section доходит до рабочей границы, меняется только дочерняя надпись; основная page label остаётся. Уход/приход ограничены внутренней маской, не пересекают бирку/города. Scroll reversal обращает то же состояние, остановка останавливает прогресс. В reduced motion — доступная статичная композиция без пролёта, не исчезновение функций.

## 6. Проверенный source gap, а не утверждение о готовом runtime

Fresh-read events-bot-new executable branch на **414a9cf103e77345132afc9b08e0147446d6496a**:

[EventLayout.astro](https://github.com/onedayonemasterpiece/events-bot-new/blob/414a9cf103e77345132afc9b08e0147446d6496a/site/src/layouts/EventLayout.astro), `HEADER_NAVIGATION` содержит восемь keys: today, tomorrow, weekend, exhibitions, festivals, popular, unusual, clubs. Однако `visibleHeaderNavigation` явно фильтрует:

```ts
item.key !== 'popular' && (item.key !== 'clubs' || INTEREST_CLUBS_PUBLIC_ENABLED)
```

Это конкретное расхождение с новым выбранным вариантом: наличие popular в исходном массиве ещё не означает видимый пункт. Перед удалением desktop floating-page identity нужно вернуть подходящий visible/selected пункт **в реально используемую presentation существующего menu owner**, а не только поправить массив, который не отрисовывается. Проверить также CSS, альтернативный Reference4 view, текущие active-state и feature gates. Это dependency реализации, не кодовое исправление в этом документальном ходе.

«Клубы» и другие feature-gated destinations не включать в production только потому, что они показаны в полной illustrative схеме. Состав берётся из актуального resolved navigation registry, порядок/назначение и один current state сохраняются. Никаких выдуманных «Места / Журнал» или добавочного Search-кружка из прежних сгенерированных картинок.

## 7. Что сохраняется без переработки

Брендовая бирка статична относительно соседней композиции. Нижний dock остаётся **одним цельным островом**; отклонённая тяжёлая desktop skin не возвращается, новое macOS-like оформление не утверждается этой схемой. Карточки/постеры/геометрия выдачи, ranking, профиль и transport не меняются.

Exact Free по полной смысловой эквивалентности может использовать один canonical медальон вместо floating-названия. H1/доступное имя/qualifiers и image-error text fallback остаются. Неизвестный asset или богатый scope не подменяются похожей пиктограммой.

Города сохраняют исходные controls/filter/storage owner, selection, immediate-apply policy и working close/Escape/focus. Переполнение не создаёт второй набор рассинхронизированных checkbox. Small-height/Popover-unavailable flow занимает настоящее место во всех родительских grid tracks; после расширения восстанавливается подходящее представление.

Общий shell читает actual rects и координирует размещение; нет нового document scroll owner. Safe area один раз; прозрачные промежутки не перехватывают click; no focus/Stop/held-control obstruction; nav XOR CTA и modal/gallery lifecycles сохраняются. FI/RB receipts, exposure/served, frozen prefix, exact hide/undo, optional analytics OFF и отсутствие raw-input telemetry не ослабляются.

## 8. SVG-состояния текущей итерации

Подготовлены отдельно editable SVG для desktop1440 и1920, по четыре состояния: исходный экран с полным menu/city набором; общая строка; handoff; следующий section. Дополнительно mobile390 показывает одно combined page+section surface. Примитивы и текст, без растровых вставок, фотографий, image generation и font-file embedding. Полки/города/размеры — specimen inputs, не изменённая live taxonomy или approved tokens.

HTML — **просмотрщик состояний**, не демонстрация готовой scroll-анимации или работающих product filters. В нём можно переключить размеры/состояния и сохранить текущий SVG. Предыдущие SVG/GIF v1.4 и сгенерированные растровые boards не доказывают этот вариант и не используются как source geometry.

Выполнены12 локальных проверок векторной модели: валидный XML; полнота menu/cities исходного состояния; visible current; сохранность overflow destinations; реально видимые городские варианты; one-row fit; неподвижная бирка между состояниями; отсутствие duplicate page title в desktop shelf island; mobile double identity без desktop menu; неизменность menu/cities при handoff; отсутствие embedded rasters. Отрисованные для внутренней проверки SVG просмотрены. Это не браузерная приёмка Astro, не native Penpot и не A=S=P.

Артефакты этого хода переданы в `/mnt/data/popular-nav-correction-v15/`; sandbox paths — только файлы разговора, **не GitHub blobs или опубликованный сайт**. Этот commit сохраняет нормативное решение в существующем source document. Проверки схемы не переносятся в старые CI totals #638.

## 9. Точная граница дальнейшего внедрения

Перед implementation читать current HEAD/#621 и не накладывать новый controller поверх параллельного top-band runtime. Проверить существующие authoritative menu sources, condition наличия видимой page identity, active-state на direct load/Back/Forward, текущие component versions и resolved composition. Desktop menu и mobile brand должны остаться своим одним owner.

Приёмка нового поведения: (1) desktop имеет настоящее меню и видимое selected «Популярное»; (2) floating context только section; (3) города initial expanded и затем measured partial/overflow без потери фильтра; (4) mobile — одна двойная surface без добавочной nav полосы; (5) смена полки не меняет selected page/cities; (6) constrained viewport/zoom никогда не теряет page identity; (7) H1/H2/accessibility/focus и no-JS сохраняются; (8) actual source-bound S/P фиксирует mode `nav-represented` либо `combined-page-section`, полную navigation membership, active key, видимые/overflow элементы, asset IDs и geometry.

Эта итерация не изменяет production, runtime, shared foundations, canonical components или STATUS. Public same-corpus Kaggle preview, реальный native P и завершение нормализации не заявлены. Прежний #638 diagnostic checkpoint относится только к тому исходнику и city-fallback repair, а не к новому desktop menu решению.
