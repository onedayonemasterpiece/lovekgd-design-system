Это текущий владелец согласованных UI-решений; [core FI-01–20](system-design-v1.md) и [RB-01–03](release-bindings-v1.md) действуют с адресными уточнениями здесь. [Предыдущая v1.7](https://github.com/onedayonemasterpiece/lovekgd-design-system/blob/5058b93b1040eda78cb85e102d369d3e1592f0a0/docs/research/floating-control-islands-2026-08/top-row-composition-v1.1.md) остаётся историей, не параллельной authority.

**Добавлено по последним словам владельца:** центрирование городской полки; особая нормализация двухколоночного Weekend и заголовков обоих дней; постановка на реализацию по всем пользовательским архетипам. ## 1. Цель и область применения

Чистый контентный интерфейс: на обычном первом экране уже видны реальные события, а не только управление. Островы сохраняют контекст и достижимость действий при чтении, не создают много независимых закреплённых этажей. Число и состав ролей определяется задачей страницы; «внедрить на всех» не означает добавить города, полку или composer туда, где их нет.

Все реальные пользовательские archetypes/варианты входят в source integration и проверки. Admin/lab/diagnostic страницы не входят в продуктовый redesign; registry/catalog/preview index служат инструментами проверки. Пользовательские формы, информационные страницы, saved/personal surfaces не исключаются как «служебные» только из-за названия. Feature gates сохраняются. Матрица текущих consumers уточняется по actual registry/manifest, не вечным списком из старой схемы.

Кожаная бирка «Полюбить Калининград Анонсы» **не меняется** от соседей: не сжимается, не переезжает и не получает новый glyph/motion. Её собственное открытие/закрытие остаётся. Нижний dock — **один цельный остров**. Отклонённая тяжёлая широкая desktop skin не возвращается; будущее macOS-like оформление остаётся отдельным visual candidate, не условием починки других consumers.

Растровые генерации, где появились «Главная / Афиша / Места / О проекте», дополнительный Search-кружок, чужие карточки или условно выбранная суббота, не являются источником требований. Генерацию картинок для этой задачи не использовать. Схемы — только иллюстрации; actual component geometry/assets берутся из source и resolved Astro.

## 2. Desktop: правое меню, обычный H1 и компактизация только по необходимости

После закрепления:

```text
[неподвижная бирка] [контекст текущей полки / задачи] [города]    [меню разделов]
                                                               ↑ правый край
```

Меню — существующая навигация «Сегодня / Завтра / Выходные / …» с видимым выделенным текущим пунктом и `aria-current="page"`. Это ссылки между страницами, не новый toggle/tablist/menu framework. Состав/порядок/feature gates берутся у actual owner. Не прятать selected «Популярное» в overflow, продолжая считать название страницы видимым.

**До прокрутки меню полное, если помещается СЕЙЧАС.** Не резервировать заранее будущую плотную строку и не сворачивать пункты из-за ярлыка1440/1920 или самого scroll offset. Постоянен правый anchor с существующим безопасным отступом, а не навсегда постоянная ширина. При настоящем дефиците может измениться левая граница menu surface; при возвращении места — обратимое расширение с hysteresis. В пределах одного fit-profile смена полки не заставляет menu targets двигаться.

Обычный desktop H1, например «Популярное», уходит за верх вместе с документом. Когда selected item реального меню уже сообщает страницу, **в floating context остаётся только полка**. Дублирующий плавающий H1 не появляется. На страницах, не представленных видимым пунктом меню, сохраняется необходимая page identity: осмысленный locator/named trigger/combined context, а не пустой принцип «на desktop все названия убрать».

Города изначально — ряд доступных вариантов, не один заранее закрытый dropdown и не открытое на весь экран окно. При реальной нехватке ширины сначала сокращается городская группа до достаточного partial/summary представления; затем при необходимости — неактивные nav destinations. «Ещё города» и «Ещё разделы» имеют разные названия/содержимое. В очень тесном desktop допустим named current-page navigation trigger; безымянные точки не заменяют page identity.

Fit определяется фактическими bounds/шрифтом/safe area/minimum targets в текущем состоянии. Никаких tiny labels, clipping и дополнительных постоянных sticky полос ради формального «всё в ряд». Фокус, pointer-held, IME и открытое раскрытие защищены; cosmetic compaction не подменяет активный control. Смена выбранной полки сама по себе не rerank, навигация или новый page view.

## 3. Центрирование полки городов

**До закрепления:** если города находятся на самостоятельной строке, видимая группа центрируется относительно её действительного контентного контейнера, сохраняя безопасные края. Не по левому краю пустой широкой подложки; не растягивать каждый chip, чтобы заполнить всё место.

**В общей desktop строке:** сначала учитываются неподвижная бирка, левый контекст и правое меню. Городам выделяется свободный диапазон между левыми участниками и меню. Видимая группа городов центрируется **в этом диапазоне**, а не любой ценой относительно всего экрана, где центр мог бы оказаться под меню.

В одной системе CSS-координат:

```text
slot_left  = rightmost occupied edge слева + accepted gap
slot_right = actual menu.left − accepted gap
group_left = slot_left + (slot_width − measured_visible_group_width) / 2
```

Формула применяется только к уже помещающемуся permitted view. При отрицательном запасе сначала выполняется реальный fit/overflow, затем центрирование. Safe area не прибавляется второй раз. Пустые промежутки остаются прозрачными для hit testing; обязательной full-width подложки нет.

В pinned состоянии scope slot резервируется по читаемому profile, а не меняет ширину от каждого заголовка. Поэтому handoff полок не дёргает города/меню. Изменение состава/viewport может пересчитать центровку на безопасной границе взаимодействия. Если городских controls нет, пустой городской остров не рисуется. Центрирование не меняет выбранный город, порядок событий или membership.

## 4. Mobile и смена контекста

На mobile нет дополнительной горизонтальной desktop-навигации. Разделы доступны через existing branded menu. «Популярное» с первых пикселей scroll начинает плавно сокращаться и **двигаться диагонально**, без этапа «сначала вбок, затем вверх». Поверхность появляется постепенно. Траектория не пересекает реальную бирку; уменьшение и движение рассчитываются совместно из actual endpoints, не из условной схемы. Нет двух одновременно читаемых названий или позднего клона после исчезновения H1.

Page label и дочерний контекст — **одна поверхность, два типографических уровня**. На короткой странице/без полки не добавлять пустой второй ряд. Рядом отдельный city trigger той же фактической высоты, общего top/bottom alignment и согласованного материала/radius. «…» уменьшает ширину, не превращает кнопку в низкий кружок возле высокого соседа. При нужном wrap обе поверхности растут вместе; glyph обычного оптического размера. Никаких обязательных64/80px из прежних specimens.

Когда к рабочей границе подходит следующая последовательная полка, прежняя дочерняя надпись уходит вверх, новая приходит снизу внутри своего слота/маски. На mobile page label остаётся; на desktop selected navigation не меняется. Обратный scroll восстанавливает предыдущий scope, остановка останавливает движение; после конца последней полки контекст не зависает над footer. Короткие/пустые/динамически обновлённые sections не порождают stale titles.

H1/H2, anchors, heading navigation и единственные реальные controls остаются семантически корректными. Motion не создаёт второй scroll/heading owner, scroll hijack или повторное объявление каждой геометрии. Reduced motion/no-JS дают читаемую доступную композицию без пролёта, а не потерю функций. Native keyboard/zoom/focus safety проверяются отдельно от видео анимации.

## 5. Weekend: две равноправные колонки, не одна активная полка

Последняя owner-постановка: страница «Выходные» сложнее обычной выдачи — две desktop колонки, горизонтальная навигация дат/времени, общая строка floating controls; заголовки субботы и воскресенья нужно сделать современными и лаконичными.

**Проверенные owners @events64f634207:** `WeekendListingSurface.astro` содержит `WeekendRangeNav` для других выходных, `ListingWeekendTimeNav`/`ListingTimeNav` для частей дня/точного времени, `WeekendEditorialTimeline` с обоими днями, day headers с date/count и `WeatherDateContext`, отдельную existing mobile listing presentation. Эти функции не сводятся к двум декоративным чипам «Сб / Вс».

Сохранить две одновременно читаемые desktop колонки и их соответствие дням/датам, общий time-axis/порядок where applicable и существующий единый document scroll. Не превращать их в tabs, две независимые scroll-панели, одну смешанную ленту или generic DateListing. Суббота не становится глобально выбранной только потому, что нарисована слева. Пустая суббота не меняет identity правой колонки; нельзя забивать пустоту чужими/фиктивными событиями.

**Общая строка управления:** защищённая бирка; уместный context периода/времени; города, центрированные в оставшейся области; реальное меню справа с выбранным «Выходные». Развёрнутые range/time choices доступны, пока помещаются. При дефиците текущий диапазон/время остаются именованными, остальное — в своём осмысленном раскрытии. Range links меняют период, time anchors перемещают внутри периода; их действия не смешиваются. Их полные панели не закрепляются отдельными широкими полосами одна под другой.

**Стартовый вариант для implementation-preview заголовков дней:** у левой и правой колонки одинаковая компактная структура `Суббота  ·  12 сентября` / `Воскресенье  ·  13 сентября`: день основным начертанием, реальная дата вторичным, согласованная baseline/высота. Нейтральная тонкая граница или спокойная поверхность из существующих roles, без двух тяжёлых цветных баннеров. Не дублировать `Сб` рядом с `Суббота` и ещё раз той же датой без функции. Count — тихие метаданные, не огромный badge. Сохранить необходимые weather/action semantics; дополнительные подробности не превращаются в постоянную высокую шапку.

Это выбранный **начальный candidate для review**, не уже approved skin и не разрешение сменить typography foundations. Оба day headings остаются пространственно связаны со своими колонками; не объединять их в одну капсулу «Суббота» в общей шапке.

После прокрутки допустим общий компактный content-bound ряд двух day labels над соответствующими колонками под общей строкой controls. Это **подписи двухколоночной структуры, не второе глобальное меню или два независимых island этажа**. Он имеет одного geometry owner, минимальную содержательную высоту, учитывается occupied-space и заканчивается вместе с weekend board. При недостаточной высоте labels возвращаются в поток, не отнимают экран у событий. Контекст одного дня не вытесняет другой по правилу handoff последовательных полок Popular, пока обе колонки видны.

Обязательные ситуации: populated/empty/short один из дней, одинаковое время с обеих сторон, разные месяцы/годы, воскресенье «сейчас», past/started states, нет будущих ranges, длинный город, narrow desktop/zoom, Back/Forward/deep link и сохранение выбора. No-JS не теряет даты. Mobile сохраняет свою осмысленную последовательную/адаптивную presentation; не сжимать две desktop колонки в нечитаемый телефонный экран.

## 6. Большая карточка и Free identity

`Бесплатно · Вход свободный` (любой разделитель при том же смысле) → **`Бесплатно`** на EventCard Large. Это удаление тавтологии, не всех qualifiers. Регистрация, временные/аудиторные ограничения, платный билет на площадку, отсутствие мест/закрытие/неизвестные условия остаются понятными. Не менять source description, domain facts, share или CTA всех surfaces глобальной заменой.

Одна card-presentation policy для SSR и appended cards. Не CSS-only concealment и не сокращение initial HTML при старой подписи после подгрузки. Удалённый текст не оставляет фиксированную пустую высоту; не обещается одинаковое число сэкономленных pixels на всех карточках. Actual tests сверяют label/условия/высоту и динамическое заполнение.

Exact Free collection может показывать **сам канонический медальон как остров**, без дублирующего floating-названия и пустой подложки. H1/доступное имя/return-to-title и qualifiers сохраняются. «Бесплатно с детьми» не сводится к одному `0 ₽`. До успешной загрузки/при asset failure остаётся текст. Canonical icon/medallion identity не заменяется похожим рисунком.

## 7. Owners, надёжность и границы реализации

Один existing EventLayout/shared geometry owner, существующие menu/filter/heading/keyboard/overlay controllers. City rectangle использует original fieldset/selection owner и немедленное применение; корректные Escape/outside/close/focus. Без Popover API/при малой высоте — настоящий flow, включая natural height всех родительских grid tracks, затем безопасное восстановление. Cleanup не оставляет listeners/observers, duplicated IDs или оживающие контроллеры.

Measured occupied rects с учётом scope/lane, safe area один раз, прозрачные gaps не перехватывают input. Focus/held pointer/IME/Stop защищены. Nav XOR CTA, gallery/modal/nonmodal distinctions и timers остаются existing semantics. Error/action/unknown не исчезают как passive toast.

RB-01–03 остаются обязательны: правдивый receipt state; delivery/gateway/profile/analytics у прежних owners; фактическая видимость/served order; frozen visible prefix и exact global hide/undo; optional analytics OFF не ломает продукт. Не логировать raw input/audio/PII ради layout. Search viewed/refinement/pending не смешиваются. Реальный voice/backend не реализуется новым chrome controller.

Shared foundations, cards/media/grid/ranking не перепроектируются, кроме явно указанной card-label presentation и необходимого owner-bound layout. Сохраняй более поздние согласованные правила кадровки из latest integration: не возвращай старый crop veto или непринятый card layout по устаревшему research документу.
