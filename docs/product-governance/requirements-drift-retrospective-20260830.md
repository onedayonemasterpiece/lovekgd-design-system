# Ретроспектива дрейфа требований Astro ↔ UI SoT ↔ Penpot

**Дата:** 2026-08-30

**Статус решения:** `ACCEPTED`

**Результат:** принят один канонический A=S=P contract, один страничный
профиль и обязательный change-control `БЫЛО → БУДЕТ → СОГЛАСОВАНО`.

**Canonical contract:**
`onedayonemasterpiece/lovekgd-design-system/docs/product-governance/astro-sot-penpot-conformance.md`

**Version / commit:** `1.0.0` /
`7607143afc240b9f96abd51270ab82735aabf9bc`

**Content SHA-256:**
`75c70629f01f8d60fb98290fa2e6e8abc201fc84885339c16010bcd75ddd4289`

## 1. Что происходило

Правила качества существовали, но были распределены между handoff-файлами,
длинными промптами, receipts, комментариями владельца и локальными планами
исполнителя. Каждое новое окно фактически заново компилировало требования.

Из-за этого возникали повторяющиеся классы дрейфа.

| Дрейф | Как проявлялся | Продуктовый ущерб |
|---|---|---|
| Продуктовая цель превращалась в технический план | `WIP=1` был переосмыслен как обязанность сохранить один task-контейнер, хотя смысл был в одной активной странице | Работа остановилась из-за оркестратора, а страница не стала reviewable |
| Гипотеза становилась обязательным требованием | Конкретная central reconstruction/materializer-схема передавалась как единственно допустимый путь | Агент мог корректно выполнить план и всё равно не решить пользовательскую проблему |
| Структурный PASS конкурировал с визуальным результатом | validation, lineage и receipts росли быстрее, чем готовая owner-review surface | Техническая доказательность подменяла возможность владельца реально посмотреть продукт |
| Tool blocker становился терминальным итогом | Невозможность продолжить старый Codex task объявлялась результатом | Пользователь снова занимался переносом внутренней операционки |
| Требования копировались между окнами | Каждый handoff повторял A=S=P своими словами | Терялись нюансы, появлялись новые запреты и расходились определения PASS |
| Authority и fixture lineage дрейфовали | mobile-v3 мог содержать desktop-v2 или metadata другого fixture | Формально linked дерево не гарантировало фактическое соответствие страницы |
| Статусы становились нестрогими | READY/blocked описывали состояние процесса, а не готовность поверхности к ревью | Владелец не понимал, что именно уже можно проверить |
| Изменения требований не имели явного протокола | Новая инструкция могла молча отменить старую или быть проигнорирована как «противоречащая» | Машина и владелец смотрели на разные версии правил |

## 2. Корневая причина

Не отсутствие правил, а отсутствие **одного нормативного владельца правил**.

Handoff должен описывать состояние и дельту. Receipt должен доказывать результат.
Промпт должен запускать работу. Ни один из них не должен становиться новым
источником глобальных требований.

## 3. Критически важное правило

> Для всех Astro ↔ UI SoT ↔ Penpot задач существует один versioned normative
> contract. Все окна, агенты, репозитории, Penpot-файлы, page profiles и receipts
> ссылаются на один и тот же contract SHA. Глобальные требования не копируются
> в промпты. Нижестоящий документ не может молча переопределить вышестоящий.

## 4. Не один гигантский файл, а один канон

Минимальная модель:

1. Один канонический Markdown contract — общие правила и продуктовые gates.
2. Маленькие page profiles — только маршрут, fixtures, states и локальные
   критерии; без повторения глобальной политики.
3. Pointer/lock в каждом репозитории и Penpot-файле — contract version + SHA.
4. Receipt — доказательство по конкретному profile и contract SHA.

Таким образом, нормативный источник один, а данные конкретной страницы остаются
маленькими и проверяемыми.

## 5. Иерархия

1. Canonical A=S=P contract.
2. Page profile.
3. Approved change record / bounded exception.
4. Baseline receipt and evidence.
5. Task prompt / handoff delta.
6. Agent plan.
7. Logs.

Ни один пункт ниже не изменяет пункт выше.

## 6. Изменение требований

При явном конфликте агент обязан показать:

- **БЫЛО** — точное действующее правило;
- **БУДЕТ** — точное новое правило или page exception;
- **ЗАЧЕМ** — продуктовая причина;
- **ПОСЛЕДСТВИЯ** — затронутые страницы, миграция и риски;
- **ТИП** — global amendment или bounded page exception;
- **СОГЛАСОВАНО** — решение владельца.

После согласования сначала меняется и версионируется канон, затем реализация.
Молчаливая переинтерпретация запрещена.

## 7. Что должно исчезнуть из будущих промптов

Не нужно вручную переносить:

- полное определение A=S=P;
- общие запреты screenshots/detached/local masters;
- глобальное определение READY_FOR_OWNER_REVIEW;
- старые WIP/task IDs;
- предпочитаемую архитектурную гипотезу;
- длинную историю всех неудачных попыток.

Новый prompt передаёт product scope, contract/profile SHA, baseline receipt и
дельту. Остальное агент обязан fresh-read сам.

## 8. Принятая минимальная реализация без бюрократии

- `lovekgd-design-system/docs/product-governance/astro-sot-penpot-conformance.md`
- `lovekgd-design-system/contracts/page-profiles/free-collection.owner-review.v1.yaml`
- короткие routing pointers в применимых `AGENTS.md` обоих репозиториев;
- immutable repository locks;
- `requirements_contract` lock в Penpot shared plugin data и receipts до принятия соответствующей поверхности.

Исторические handoffs не мигрируются и не переписываются. Они перестают быть
нормативными.

## 9. Упрощённый критерий бесплатной подборки

> Penpot desktop/mobile показывает те же пять реальных бесплатных событий, что
> deterministic Astro: те же данные, порядок, изображения/crop, переносы,
> действия, counts, shell и навигацию. Принятые поверхности состоят только из
> связанных центральных native components, без detached, screenshots,
> route-local masters и stale nested data. Fresh exports визуально проверены,
> tests/push/readback завершены — после этого READY_FOR_OWNER_REVIEW.

Технический способ достижения этого результата агент выбирает сам.


## 10. Принятое решение

Proposal принят 30 августа 2026 года как contract `kenigevents.asp-conformance`
v`1.0.0`, status `ACTIVE`. Единственный нормативный owner находится в
`onedayonemasterpiece/lovekgd-design-system`. `events-bot-new` является
consumer и хранит только immutable lock и routing pointer.

Исторические handoffs, receipts, evidence и agent plans не мигрируются и не
становятся конкурентными sources of truth. Их роль — состояние, доказательства
и дельта. Настоящее изменение требований сначала согласуется и фиксируется в
каноне; только после этого обновляются locks и реализация.
